# RosenBridge — .NET Implementation Notes

Status: design proposals. Wire rules are described in spec.md; this document covers technical choices for the .NET implementation.

## Core approach: an abstraction over TCP

- RosenBridge provides session, channel, message, and stream APIs over the existing TCP facilities supplied by the operating system and language/runtime.
- The TCP stack, packet ordering, retransmission, and congestion control are left to the platform implementation.
- The .NET implementation uses the platform's socket/TCP and TLS facilities. RosenBridge manages connection lifetimes, message boundaries, transfers, and application resource limits.
- RB/1 framing and control messages in the specification are the application-level wire contract between the two ends of this abstraction; developing a separate transport stack is not a goal.
- Framing and control-message codecs are internal to the core Stella.RosenBridge assembly; there is no separate protocol assembly.

## Payload and request/response API direction

The working Channel API is documented in [docs/channel-api.md](docs/channel-api.md). Channel acquisition through the management connection and TLS/upper-layer acceptance callbacks are documented in [docs/client-server-api.md](docs/client-server-api.md). A Channel owns its data connection; the client owns its management session.

- All payloads are streams. Individual messages/byte arrays and input streams use the same transfer path; full-payload buffering is not the default.
- The request writer and response reader must be independently accessible through the same operation handle. Access to the response must not wait for request transmission to finish.
- Ending the local writing direction and waiting for peer consumption acknowledgement are separate operations. Helpers must not require waiting for peer acknowledgement before response reading starts.
- A request handler may write a response while reading the request. Broker integration is not a prerequisite.
- A channel is a logical endpoint that accepts multiple TCP/TLS connections. Each connection carries one request/response operation and closes when it ends. Connections do not multiplex operations on the same socket.
- Tickets and capacity reservations are per connection. Closing a connection does not close its channel endpoint or other connections.
- The framing candidate uses a chunk header with a length and END flag; the payload is not scanned for magic bytes. If the final input chunk is not known in advance, a separate empty END chunk can be sent. The wire encoding is not final.

## Hosting boundaries

`Stella.RosenBridge.Hosting` supplies common DI registration, channel scopes, and Generic Host lifecycle management. `Stella.RosenBridge.Hosting.AspNetCore` adds an HTTP/1.1 Upgrade entry point and client adapter on the existing web port. TCP acceptance and TLS setup remain separate from processing an externally accepted connection. Both adapters use the same core session, ticket, and channel implementation. See [hosting.md](docs/hosting.md) for the implemented APIs and limits.

## Control JSON and serialization

- Fixed control DTOs can use System.Text.Json source generation and JsonSerializerContext. Serializing/deserializing directly through generated JsonTypeInfo removes the need for reflection-based fallback.
- Source generation alone does not guarantee zero allocation. DTO, string, collection, and output-buffer allocations must be measured separately.
- Prefer reading/writing directly from UTF-8 buffers. If needed on hot paths, Utf8JsonReader/Utf8JsonWriter can process only the required fields.
- Do not assume the serializer's defaults satisfy the wire rules. In particular, duplicate-key rejection, required fields, ID ranges, and case sensitivity must be validated separately; a bounded validation pass may precede source-generated deserialization.
- Metadata/serializer options and buffers may be reused within appropriate lifetimes. Do not share mutable reader/writer state between concurrent operations. Define ownership and cleanup for buffers carrying tickets and authentication data.

## Verification goals

1. Control-message round-trip and invalid-input tests with reflection fallback disabled.
2. An actual NativeAOT publish and smoke tests against the published binary covering session authentication, multiple ticket-bound connections to the same channel, and concurrent request/response. Code generation alone does not count as AOT verification.
3. Measure allocated bytes/op, CPU, and latency for small control messages and frequent operation-connection creation/closure; compare DTO deserialization with direct reader processing.
